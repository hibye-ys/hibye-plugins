# Claude 모델 배정

입력: `$ARGUMENTS`

- `refresh` 이면 아래 "카탈로그 갱신"만 한다.
- 비어 있으면 지금 대화의 진행 중 작업을 대상으로 한다.
- 그 밖에는 입력을 작업 설명으로 보고 배정한 뒤 실행한다.

모델 버전·가격·작업별 시작점·실측 수치는 [catalog.md](catalog.md) 에 있다. 배정 전에 읽는다.
이 스킬은 Claude 모델만 다룬다. 다른 제공자(Codex 등)에 맡기는 단계는 배정표에 "외부"로 적고 해당 스킬에 맡긴다.

## 배정 원칙

1. **기본은 opus·medium.** 확실하지 않으면 여기서 시작한다.
2. **작은 모델은 실수가 쉽게 드러나는 일에 쓴다.** 찾기·실행·로그 읽기·요약·기계적 갱신은 haiku 또는 sonnet 서브에이전트에 맡긴다.
   코드 편집과 판단은 메인 모델에 둔다. 단, 범위와 스펙이 명확한 코딩은 sonnet 에 맡길 수 있다.
3. **리드 + 저렴한 워커는 병렬로 나눌 수 있을 때만 쓴다.** 독립 조각이 여러 개면 opus·fable 리드가 나누고 sonnet·haiku 워커가 처리한다.
   의존성이 한 줄로 이어지거나 한 컨텍스트에 들어가는 작업은 나누지 않는다. 나누면 오히려 손해다.
4. **비싼 메인 컨텍스트는 판단에만 쓴다.** 긴 파일·로그 읽기는 서브에이전트에 맡기고 결론만 받는다.
5. **사람이 기다리는 응답은 지연을 우선한다.** sonnet low~medium.
6. **opus high 로도 부족하면 opus 를 더 올리기 전에 fable 을 먼저 시험한다.**
7. 단계 유형별로 고정 규칙이 서면 모델에게 고르게 하지 말고 규칙대로 배정한다.

## 올리는 순서 (성능이 부족할 때)

1. 모델이 스스로 확인할 수 있는 검증 수단(테스트·빌드·스크립트)을 먼저 붙인다.
2. effort 를 한 단계 올린다. high 를 넘으면 더 큰 모델만큼 비쌀 수 있다.
3. 그래도 안 되면 한 단계 큰 모델로 옮기고 낮은 effort 부터 다시 시작한다.

- effort 는 모델에 없는 지식·기술을 주지 못한다. 지식이 부족한 실패면 바로 3으로 간다.
- 같은 작업을 여러 개 돌리면 낮은 effort 로 먼저 돌리고 **실패한 것만** 높은 effort 로 재실행한다.

## 모델을 섞을 때 비용

- 캐시는 모델별로 따로다. 진행 중인 맥락을 다른 모델로 넘기면 캐시를 처음부터 다시 쓴다. 넘길 때는 전체 대화 대신 요약을 넘긴다.
- 상위 모델의 thinking 은 하위 모델로 넘어가지 않는다. 같은 추론을 이어가야 하는 단계는 같은 모델에 둔다.
- `opusplan`(계획 opus·실행 sonnet)은 원칙 2와 반대다. 기본으로 쓰지 않는다.
- advisor(실행 모델이 도중에 상위 모델에 조언을 구함)는 실행 모델이 sonnet·haiku 일 때 권장된다. 이미 opus·fable 이 실행하면 이득이 적다. 쓰려면 먼저 자문 빈도를 잰다.

## 실행 절차

1. 작업을 단계로 나눈다. 단계마다 성격(탐색·기계적·구현·판단·검증), 의존 관계, 병렬 가능 여부를 적는다.
2. 단계마다 `model`·`effort` 와 이유 한 줄을 배정표로 보여 준다. 메인 세션이 직접 할 단계는 "직접"으로 적는다.
3. 배정대로 실행한다. 모든 Agent 호출과 workflow `agent()` 에 `model`·`effort` 를 명시한다.
4. 서브에이전트에는 목표·대상 파일·완료 기준·건드리지 말 것·돌릴 검증 명령을 담는다.
5. 끝나면 배정표 옆에 실제 결과(성공·실패·재시도·올린 단계)를 붙여 보고한다. 이 기록으로 사용자가 규칙을 조정한다.

## 카탈로그 갱신 (`refresh`)

1. catalog.md 맨 위의 출처 글과 공식 문서(Choosing a model, Effort)를 다시 읽는다.
2. 새 모델·가격·기본 effort·작업별 시작점 변경을 catalog.md 기준 diff 로 보여 준다.
3. 사용자가 확인하면 반영하고 확인일을 갱신한다. SKILL.md 원칙이 바뀌어야 하면 따로 제안한다.
