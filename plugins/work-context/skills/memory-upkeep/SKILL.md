# 메모리 정리

메모리 노트는 다음 세션이 읽고 그대로 믿는다. 그래서 틀린 노트는 없는 노트보다 나쁘고, 코드가 바뀌면 노트는 저절로 낡는다. 매 세션 들어가는 인덱스가 길어지면 정작 필요한 노트가 읽히지 않는다. 이 스킬의 목표는 두 가지다. 다음 세션이 **지금 작업에 필요한 노트를 찾을 수 있고**, 찾은 노트를 **믿어도 된다**.

노트를 많이 남기는 것이 목표가 아니다. 화면이나 코드에서 바로 읽을 수 있는 사실은 메모리에 둘 필요가 없다. 스스로 알아내야만 생기는 것(검증된 규칙, 함정, 사용자가 정한 방식)이 메모리에 남을 것이다.

## 1. 이 프로젝트의 메모리를 먼저 파악한다

프로젝트마다 구조가 다르다. 다른 프로젝트의 모양을 가정하지 말고 아래를 직접 확인한다.

- **노트와 인덱스의 위치.** 설정 파일(예: `.work-context.json`), 지침 파일(`AGENTS.md`·`CLAUDE.md`)이 가리키는 곳을 본다.
- **무엇이 매 세션 들어가는가.** 지침 파일이 인덱스를 통째로 불러오는지, 경로만 안내하는지. 통째로 들어가는 파일의 크기가 곧 매 세션 비용이다.
- **규칙이 사는 곳.** 운영 결정 문서, 지침 파일, 작업별 스킬처럼 "지켜야 할 것"을 적는 자리. 노트가 규칙으로 옮겨졌는지 판정할 때 대조한다. 그 자리의 본문이 매 세션 들어가는지, 경로만 안내되는지도 함께 확인한다. 4절에서 규칙이 된 노트를 지울지 정할 때 쓴다.
- **작업 종류.** 지침 파일의 작업별 스킬 표처럼 프로젝트가 이미 나눠 둔 작업 영역. 작업별 인덱스의 이름은 여기서 가져온다.
- **변경이 들어가는 길.** 작업 브랜치와 PR, 필수 검사, 메모리 인덱스 점검 명령이 있는지.

프로젝트에 메모리에 관한 규칙이 이미 있으면 그 규칙이 이 스킬보다 우선한다.

## 2. 이번에 볼 범위를 정한다

- **전체 점검**: 처음 정리하거나 사용자가 전부 보라고 했을 때. 모든 노트를 본다.
- **주기 점검**: 지난 정리 이후 달라진 것만 본다. 지난 정리 커밋(커밋 메시지에 `memory-upkeep`이 들어간 가장 최근 커밋) 뒤로 (가) 새로 쓰였거나 고쳐진 노트, (나) 가리키는 파일·명령이 그 뒤에 바뀌거나 사라진 노트를 고른다. 사용자 선호처럼 코드와 무관한 노트는 주기 점검에서 다시 보지 않는다.

사용자가 범위를 따로 정해 주면 그 범위만 본다.

주기 점검에서 고른 노트가 없으면 "바뀐 것 없음"이라고만 보고하고 끝낸다. 빈 변경으로 PR을 만들지 않는다.

모든 노트를 매번 다시 검증하는 것은 비용만 든다. 변하기 쉬운 노트(경로·명령·수치를 담은 것)에 힘을 쓴다.

## 3. 노트마다 두 가지를 판정한다

노트를 전문으로 읽고, 추측하지 말고 레포에서 확인한다. 판정마다 확인한 파일과 줄, 또는 실행한 명령을 근거로 남긴다. 근거 없는 판정은 판정이 아니다.

**상태**

| 상태 | 뜻 |
|---|---|
| 유효 | 지금도 맞다 |
| 일부 낡음 | 교훈은 맞는데 본문의 경로·명령·수치가 낡았다 |
| 낡음 | 가리키는 장치·구조가 사라져 더는 적용되지 않는다 |
| 규칙으로 옮겨짐 | 같은 내용이 규칙이 사는 곳에 이미 있다 |
| 중복 | 다른 노트와 교훈이 겹친다 |

- 확인할 대상이 레포에 없으면(사용자와 일하는 방식, 답변 방식 등) 유효로 두고 "확인 못 함"이라고 적는다. 이런 노트를 낡았다고 판정할 수 있는 것은 사용자뿐이다.
- 노트가 가리키는 경로가 지금 있는지 먼저 기계적으로 훑으면 볼 곳이 좁아진다. 다만 경로가 없다는 것은 단서이지 판정이 아니다. 파일이 옮겨졌을 뿐 교훈은 그대로일 수 있다.
- 노트와 운영 결정이 서로 어긋나면 어느 쪽이 맞는지 고르지 않는다. 그대로 두고 사용자에게 알린다.

**칸**

| 칸 | 넣을 것 |
|---|---|
| 매번 주입 | 어떤 작업에든 걸리고, 모르면 찾아볼 생각조차 못 한 채 실수하게 되는 교훈 |
| 작업별 | 특정 종류의 작업을 할 때만 쓰이는 교훈·함정 |
| 찾을 때만 | 한 번 있었던 작업의 경과, 사고 이력, 사라진 장치의 기록 |

매번 주입의 가치는 "찾아볼 것이 있다는 사실을 몰라도 되게 해 주는 것"이다. 작업 맥락에서 자연히 찾게 되는 노트는 작업별로 내린다. 애매하면 매번 주입에 둔다. 내린 노트는 그 작업의 인덱스가 읽히지 않으면 같이 읽히지 않기 때문이다.

노트가 많으면 묶음으로 나눠 하위 에이전트에게 읽히고, 판정과 근거를 표로 돌려받는다. 판정은 보고일 뿐이다. 고치거나 지우거나 옮기는 노트는 전부 직접 읽고 근거를 다시 확인한다. 그대로 두는 노트는 보고에 기대도 되고, 그렇게 했다고 보고에 적는다.

## 4. 상태에 따라 고친다

- **일부 낡음**: 본문의 경로·명령을 현재 것으로 고친다. 현재 대응물을 찾지 못하면 그 줄이 당시 기록임을 밝혀 둔다. 교훈 문장은 바꾸지 않는다.
- **낡음**: 지울지 "찾을 때만" 칸에 남길지를 아래로 가른다.
  - 사라진 장치의 절차·상태만 담은 노트는 지운다. 장치가 없으니 읽을 일이 없고, git 이력에 남는다.
  - 다른 노트가 근거로 인용하는 기록, 사용자의 결정과 그 이유가 담긴 기록, 같은 종류의 사고가 다시 나면 찾아볼 경과는 "찾을 때만" 칸에 남긴다.
  - 어느 쪽이든 다시 쓸 교훈이 섞여 있으면 그 교훈만 짧은 노트로 살린다.
- **규칙으로 옮겨짐**: 규칙 문장만으로는 알 수 없는 **적용 방법**(어떻게 판별하는지, 어떤 경우에 예외인지)이 노트에 더 있을 때만 남긴다. 사고가 어떻게 났는지의 경과만 더 있으면 지운다. 사고 사례는 거의 모든 노트에 있어서, 사례가 있다는 것만으로 남기면 아무것도 지워지지 않는다.
  - 남길 때는 규칙이 어디 있는지 한 줄 적고, 그 작업의 인덱스에 배경으로 둔다. 작업을 가리지 않는 노트면 매번 주입 칸에 그대로 둔다.
  - 규칙 본문이 매 세션 들어가지 않는 프로젝트에서는(경로만 안내되는 경우) 매번 주입 칸의 노트가 그 규칙을 상시로 떠올리게 하는 유일한 자리일 수 있다. 이때는 지우지 말고 사용자에게 지울지 묻는다.
- **중복**: 더 충실한 쪽으로 합치고 그 파일 경로를 유지한다. 다른 쪽은 지운다. 합칠 때 낡았거나 뒤의 결정으로 바뀐 내용은 옮기지 않고, 무엇을 뺐는지 합친 노트에 한 줄 적는다.
- **긴 작업 기록**: 기록 안에 다시 쓸 교훈이 묻혀 있으면 교훈 하나당 짧은 노트 하나로 뽑는다. 기록 자체는 "찾을 때만" 칸에 둔다.

살린 교훈 노트는 프로젝트의 기존 노트 형식을 따른다. 파일 이름은 사고가 아니라 교훈을 말하게 짓고, 어느 기록에서 나왔는지 한 줄 적는다. 칸은 다른 노트와 같은 기준(3절)으로 정한다.

상태를 다시 판정했으면 인덱스의 자리도 그에 맞게 옮긴다. 보관에 있던 노트가 아직 쓸 만하면 작업별 인덱스로 올리고, 반대도 같다.

노트를 지우기 전에 그 노트를 가리키는 다른 노트를 찾는다. 가리키는 곳은 평문으로 풀어 쓰거나, 규칙으로 옮겨진 경우 규칙의 위치로 바꾼다. 인덱스 점검은 인덱스 줄만 보고 노트끼리의 링크는 잡지 못한다.

지키는 선:

- 노트에 없던 사실을 지어 넣지 않는다. 고쳐 쓰는 내용은 레포에서 확인한 것뿐이다.
- 두 근거가 충돌하는데 어느 쪽이 최신인지 확정할 수 없으면 둘 다 두고 충돌이라고 표시한다.
- 규칙이 사는 곳(운영 결정·지침 파일·스킬)은 고치지 않는다. 노트가 규칙이 될 만하면 옮기자고 제안만 한다.
- 지우는 노트는 전부 이유와 함께 보고에 적는다. 검토하는 사람이 되살릴 수 있어야 한다.

## 5. 인덱스를 맞춘다

- 한 줄은 `- [제목](파일) — 훅` 형식이다. 훅은 "지금 이 노트를 읽어야 하나"를 판단할 만큼만 쓴다. 교훈 내용, 수치, 커밋은 노트 본문에 둔다.
- 노트 하나는 인덱스 전체에서 정확히 한 곳에만 올린다. 인덱스에 없는 노트, 가리키는 파일이 없는 줄, 두 번 올라간 노트를 찾아 고친다.
- **나누는 것은 인덱스가 커졌을 때만 한다.** 노트가 수십 개 이하라 인덱스가 한눈에 들어오면 한 파일로 둔다. 커졌으면 뿌리 인덱스에는 매번 주입 칸의 줄과 하위 인덱스 링크만 남기고, 작업별 인덱스와 보관 인덱스를 따로 둔다. 하위 인덱스 링크 옆에는 "언제 읽는가"를 적는다.
- 작업별 인덱스 안에서는 유효한 것과 일부 낡은 것·배경으로 남긴 것을 구분해 둔다. 읽는 쪽이 어느 것을 그대로 믿어도 되는지 알 수 있다.
- 뿌리 인덱스에 노트 개수 같은 파생 숫자를 적지 않는다. 다음 변경에서 바로 틀린다.
- 마지막에 인덱스 점검을 돌려 누락·끊긴 링크·중복이 없는지 확인한다. 프로젝트가 자기 점검 명령을 두었으면 그것을 쓰고, 없으면 이 플러그인의 `node <플러그인 루트>/scripts/work-context.cjs check-memory --project <checkout>`을 쓴다. 인덱스를 나눈 프로젝트는 `.work-context.json`의 `memory.subindexes`에 하위 인덱스 폴더를 적어야 이 명령이 하위 인덱스까지 센다.

## 6. 마무리한다

- 정리 결과는 프로젝트의 평소 경로(작업 브랜치와 PR)로 한 번에 올린다. 커밋 메시지에 `memory-upkeep`을 넣는다. 다음 주기 점검이 이 커밋을 기준점으로 쓴다.
- 사람이 지켜보지 않는 주기 실행에서는 병합하지 않는다. 검토를 기다리는 PR로 남긴다. 프로젝트가 검사를 통과한 PR을 자동으로 병합한다면 초안으로 연다. 틀린 정리가 병합되면 모든 세션에 퍼진다.
- 메모리 밖의 파일(코드, 검사, 규칙 문서)은 건드리지 않는다. 고쳐야 할 것을 발견하면 보고에 적는다.

## 보고 형식

PR 설명과 사용자에게 하는 보고는 같은 내용이다.

```
범위: 전체 점검 | 주기 점검(기준 커밋 <sha> 이후) | 지정 범위(<무엇>), 본 노트 N개
상태: 유효 a · 일부 낡음 b(고침 b1) · 낡음 c(지움 c1, 보관 c2) · 규칙으로 옮겨짐 d(지움 d1, 배경 d2) · 중복 e
칸 이동: 매번 주입 → 작업별 n개, … (움직인 노트 이름)
지운 노트: <파일> — <이유> (전부 나열)
새로 뽑은 교훈: <파일> ← <출처 기록>
그대로 둔 것: <판정은 했지만 바꾸지 않은 노트와 이유>
확인 못 함: <파일> — <왜 확인할 수 없었나>
사용자 결정이 필요한 것: <노트와 결정의 불일치, 충돌, 지울지 물을 노트, 규칙으로 옮길 후보>
검증: <직접 확인한 노트 수, 하위 에이전트 보고에 기댄 노트 수, 돌린 점검 명령과 결과>
```

숫자만 적지 말고, 지운 노트와 결정이 필요한 것은 하나씩 이름을 적는다. 읽는 사람이 PR을 열지 않고도 무엇이 사라졌는지 알 수 있어야 한다.
