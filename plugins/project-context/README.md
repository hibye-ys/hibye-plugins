# Project Context

A Node standard-library plugin for opt-in memory pointers and lazy operating-decision discovery. STATE and project content remain project-owned. Claude/Codex share `hooks/hooks.json`; neither manifest registers a second copy. Muse/Antigravity provide source adapters only, without a native-product acceptance claim.

## Skills

- `setup-project-context`: opt-in setup and inspection.
- `docs-boundary` (template, not a global skill): docs are human records, not execution input; control-plane authority wording, contracts/ledger/generated folder split, where documents go, pinned Git reads. The project names its folders in an AGENTS.md `## docs 경계` section.

Rule skill templates live in `templates/skills/<skill>/`. `scripts/skill-template.cjs install <skill> --project <path>` copies one into the project's `.agents/skills/<skill>/` (plus `.template-base.md` as the merge base and a `.claude/skills/<skill>` link); the project edits its copy. Shared improvements raise `metadata.template_version`; SessionStart then emits `SKILL_TEMPLATE_UPDATE <skill>` for opted-in projects, and `diff`/`update <skill>` shows and three-way merges the change (on conflict the new template waits in `.template-pending.json` until the copy is resolved). See `setup-project-context`.

## Project opt-in

```json
{"schema_version":1,"memory":{"directory":"docs/memory","index":"MEMORY.md"},"intent":{"directory":"intent"}}
```

Either feature may be `false` or omitted; at least one must be enabled. Unknown keys, absolute paths, traversal, and paths whose existing ancestors escape the declared repository are rejected. The setup tool never creates or overwrites content. Custom index names are supported for every host; no second auto/manual index is created. No config means a no-op, including unrelated non-Git folders. Opted-in non-Git and bare repositories are unsupported.

Memory and intent both come from the current checkout (`git rev-parse --show-toplevel`) and its own `.project-context.json`: a linked worktree, the primary checkout, an independent clone and a cloud clone each read and write their own memory directory. No primary checkout path is consulted, so separate Git-dir layouts work. Memory written in a worktree merges when its branch's PR merges; memory another worktree has not merged yet is not visible. Missing or inaccessible checkout memory fails visibly; there is no fallback to another checkout. Paths do not grant sandbox permissions or implement a concurrent-writer lock. Writers re-read before editing and preserve other writers.

The memory index uses relative Markdown links to detail `.md` files. Validation reports dangling/escaping links, duplicate links and unindexed files, including nested details. Optional `memory.subindexes` names a folder inside the memory directory (for example `"subindexes":"index"`): the root index links each sub-index file there once, and details linked from a sub-index count as indexed without appearing in the root index. This keeps the always-loaded root index small while every detail stays reachable; a detail is still listed exactly once across the root and all sub-indexes, an unlinked sub-index is reported as unindexed, and sub-indexes do not nest. Intent follows `## C1 · Title`, `- 규칙: Decision`, `- 갱신: YYYY-MM-DD`, and a pre-entry `설명: Area — when to read`. Sessions emit only area descriptions, IDs and paths, never rule bodies or memory detail text. Intent output has a 7 KB budget and the total session context a 12 KB budget; truncation retains the memory pointer, visible diagnostic failures and a doctor/source requery marker. Every host receives the same memory directory/index/hash pointer and lazy-read instruction.

Claude native auto memory is turned off for memory-enabled projects (`autoMemoryEnabled: false`) instead of being redirected. `autoMemoryDirectory` accepts only absolute or `~/` paths ([memory docs](https://code.claude.com/docs/en/memory)), the project `.claude/settings.json` is a tracked file, and desktop-app worktree sessions read project settings from the main checkout ([worktree docs](https://code.claude.com/docs/en/worktrees)), so no per-checkout value is possible there; `settings.local.json` and WorktreeCreate generation fail the same desktop and cloud cases. Setup removes the `autoMemoryDirectory` earlier versions wrote. Until setup is rerun, Claude sessions show `PROJECT_MEMORY_NATIVE_SETTING_STALE`.

## CLI and APIs

```sh
node scripts/project-context.cjs session-start --project /path/to/checkout --host codex --event resume
node scripts/project-context.cjs doctor --project /path/to/checkout
node scripts/project-context.cjs check-memory --project /path/to/checkout
node scripts/project-context.cjs intent-check --project /path/to/checkout
node scripts/project-context.cjs intent-session-start --project /path/to/checkout
node scripts/skill-template.cjs <list|notice|status|install|diff|update> [skill] --project /path/to/checkout
node --test tests/project-context.test.cjs tests/skill-template.test.cjs tests/runner.test.mjs
```

`session-start` accepts hook JSON from stdin (`cwd`, `workspacePaths`, `source`) and emits a SessionStart envelope. Explicit CLI project/host/event overrides input. Explicit `--host` takes precedence. Native auto-detection requires stdin `hook_event_name: "SessionStart"` plus a nonempty `session_id`. Claude proof is an exact match to the host-refreshed `CLAUDE_CODE_SESSION_ID`; Codex plugin proof is `PLUGIN_ROOT` and compatible `CLAUDE_PLUGIN_ROOT` both resolving to this executing runtime snapshot. Inherited `CODEX_THREAD_ID`, `CLAUDECODE`, or other presence-only flags do not select a host. Simultaneous proofs fail visibly as `PROJECT_CONTEXT_HOST_AMBIGUOUS`; absent proofs fail as `PROJECT_CONTEXT_HOST_UNRESOLVED`. Raw CLI callers without native proof must pass `--host codex` or `--host claude`. Projects without opt-in remain no-op. These auto-detection requirements are the minimum supported native hook environment; older hosts missing the documented fields need an explicit host adapter. All four events startup/resume/clear/compact use the same lazy contract. Visible hook failures exit 0 because hosts may discard nonzero stdout; `doctor`, `check-memory`, and `intent-check` return nonzero on invalid configured input. Optional intent/diagnostic errors do not erase valid memory pointers. Memory selection validates only the memory section, so intent errors cannot block its pointer. Direct `intent-session-start` applies the same 7 KB intent budget and requery marker. Native hook configuration keeps `additionalContextLimit: 2500`; byte budgets do not establish a token-count PASS. `tests/fixtures/large-korean-{codex,claude}-context.txt` are actual emitted output samples for independent token measurement, not measured token acceptance.

`scripts/project-context.cjs` exports synchronous CJS `resolveProjectMemory`, `inspectMemoryIndex`, `parseIntentFile`, `loadIntentLedger`, `renderIntentContext`, `intentSessionContext`, `runIntentCli`, `buildSessionStartContext`, `runSessionStartContextCli`, `loadProjectContextConfig`, `inspectProjectContext`, `runCli`, constants contract version 1 and the four events. Functions accept `{repoRoot}` and use the caller checkout, never plugin location; Git queries remove location/config override environment. `buildSessionStartContext` returns a hook envelope and accepts `host`, `event`, `resolveMemory`, `intentContext`, `readFile`, and optional diagnostic callback. `resolveProjectMemory` returns `{contract_version:2,memory_scope:"checkout",checkout_root,directory,index_path}`; the 0.3.x fields `primary_checkout`, `git_common_dir` and `configuration_warning` throw `PROJECT_MEMORY_FIELD_REMOVED` when read, so older consumers fail visibly rather than reading `undefined`. The runtime loader contract (`PROJECT_CONTEXT_CONTRACT_VERSION`) stays 1. `inspectProjectContext` returns `{ok,enabled,config,memory,intent,errors}`. `loadProjectContextConfig` returns `{enabled,repoRoot,configPath,memory,intent}`.

Copy `templates/wiring/project-context-runner.mjs` byte-for-byte for thin project entry points. Its lazy `loadProjectContextRuntime` and `resolveProjectContextPluginRoot` accept `{host?,pluginRoot?,home?,env?,spawn?}`. `pluginRoot` is an explicit fixture argument only; no environment source-root override exists. Default discovery requires enabled native user registration (Codex CLI list or Claude settings plus installed registry), exact manifest version, contract version/runtime, and no symlink anywhere in payload. It never selects an unregistered cache merely because it exists. Import is safe without an installed plugin; calling the loader is the validation boundary.

## Project hook ownership

The project installer/verification layer reserves these literal SessionStart entrypoint names for native project-context ownership: `session-start-context.mjs`, `intent-ledger.mjs`, `project-context.cjs`, `project-context.mjs`, and `project-context-runner.mjs`. A project SessionStart command containing any of these names is unsupported, including a name used by `echo`, as an argument, or in a check. This conservative literal rule prevents duplicate injection without interpreting arbitrary shell syntax. Unrelated project hooks remain allowed; the plugin's own native hook binding is outside this project registration rule.

Native host proof references: [Codex plugin hook environment](https://learn.chatgpt.com/docs/hooks#plugin-hooks) and [Claude session identity environment](https://code.claude.com/docs/en/env-vars). The installed Claude 2.1.304 hook launcher also refreshes the session identity after inherited environment values. Native product readback remains a separate acceptance step.
